# W20: architecture challenge for repository-assisted Astra

## Finding

`ASTRA_KNOWLEDGE` is a substantial, carefully scoped external memory and evidence-navigation system. It is credible as an inference-time aid: it can reduce repeated corpus reading, route a question to a curated claim and its source, preserve assumptions and caveats, and expose exact archived bytes when they are present. It does not by itself improve Astra's weights, general reasoning ability, scientific reliability, or access to missing source material. Repository-first is a good way to improve *access to existing work*; it is not evidence of an intelligence breakthrough.

The strongest objection to the breakthrough premise is an information-and-interface one: all machine-readable content is either supplied human-authored text/data/code or a deterministic transformation of it. A fixed-weight model can use retrieved material only to the extent that the model's actual interface lets it read that material, keep the relevant parts in context, and perform the required operations. A static public site supplies text and files, not a new execution environment, private weights, optimizer, durable learned parameters, or a guarantee that an agent will follow the repository's reader protocol. A clever representation can make known information cheaper to retrieve or compute over; it cannot establish arbitrary new capabilities merely by being machine-readable. In particular, encoding a problem, theorem, or program is not equivalent to proving it, executing it, acquiring an unavailable oracle, or training the model on it.

## What is actually present

The design has a small entry point (`00_START_HERE.txt`, `01_CORE.txt`), 186 result cards, ten topic routers, a SQLite/FTS5 lexical index with curated aliases, source/family lookups, bounded packet/read commands, a read-only local HTTP API, a static web export, and a content-addressed exact-byte archive. `DESIGN.md` explicitly treats the layout as workload-dependent, retrieval as lexical with imperfect recall, and stored knowledge as inference-time context rather than weight change. The contracts in `AGENTS.md` and `REPRESENTATION_CONTRACT.json` correctly separate supplied from acquired information, preserve costs/dependencies/failure domains, and keep source-reported, reconstructed, and externally reviewed status distinct.

The cards span multiple mathematical fields; for a three-domain spot check I used (i) quantum complexity / repetition (`L02-commuting-repetition`), (ii) discrepancy rounding (`N24-acquired-rational-rounding`), and (iii) reaction-network permanence (`N33-endotactic-permanence`). Retrieval put the intended card first for each targeted query. The cards are unusually good at carrying theorem interfaces and negative scope along with the headline. For example, L02 keeps the commuting-operator model and the missing certified spectral-gap application gate; N24 includes exact-mean and partition-quota contracts as well as the matroid exchange failure; N33 records the measurable-rate/classwise quantifiers, essential-source convention, proof dependencies, and unresolved external review. That is a real retrieval/context benefit, although this was a hand-picked smoke check, not a recall or answer-quality estimate.

The repository's own `indexes/VALIDATION.json` is admirably explicit: selected routing and packet-budget fixtures passed, archive hashes/SQLite integrity/navigation were checked, while `scientific_validation` is false and `astra_mastery_evaluation` is “not performed.” These package checks establish properties of the package and selected fixtures, not Astra's successful reading, theorem reconstruction, or correctness. `BUILD.json` describes 14,329 searchable documents and 162,586 chunks over 3.4 GB of original-path data; that scale makes better search, extraction, and context allocation plausible value. It does not imply that all source bytes are text-searchable, that every linked full packet is present, or that the model can consume the corpus in one pass. `README.md` itself lists absent full packets in several update streams, and the index inventory has historical build timestamps; verify current snapshot/hosting freshness before relying on a mirror as canonical.

The included executable capability is narrower than the archive's scientific scope. `tools/knowledge.py` performs local lexical retrieval, packet assembly, reading, source/family lookup, state marking, verification, and a read-only server; it makes no model calls. Static hosting exposes pages and assets. It does not expose an external Python/SymPy/SAT/CAS runtime or an Astra-facing tool server. If the remote agent only has browser/file retrieval, mathematical computation remains whatever its ordinary model/tool interface already permits. Running the local CLI adds a concrete retrieval utility, but that CLI is not automatically callable by an external Astra session.

## Achievable capability gains, ranked

1. **Reliable evidence acquisition.** Improve exact identifier lookup, query aliases, hybrid lexical/semantic retrieval if locally runnable and provenance-preserving, explicit “no source found” behavior, and query expansion over counterexamples/dependencies. Expose a compact packet with claims, assumptions, charged costs, status, failure modes, and links to the exact decisive proof. Search is the strongest current bottleneck because lexical matching and hand-curated aliases can miss a relevant record or over-rank a familiar one.
2. **Context budgeting and continuity.** Generate task-specific packets from selected cards and exact source ranges; report truncation and token-meter uncertainty; maintain a small, auditable task state. This saves prompt budget and repeated ingestion. It is bounded by actual model context, tool policy, and whether state persists across sessions. The repository correctly calls token counts estimates, not Astra-tokenizer truth.
3. **Deterministic, auditable computation.** Attach runnable domain kernels, test vectors, exact/rational arithmetic where appropriate, and independent checker scripts to selected claims. Give the agent an explicit, reachable execution interface and charge setup, input acquisition, run time, memory, numerical precision, and failures. The current archive can preserve code but an archived script is not a runnable service, and a passing finite checker does not prove a universal theorem.
4. **Human research workflow.** The source map, provenance, abstraction contracts, and negative-transfer cards can prevent rediscovery and make handoffs reviewable. This improves process throughput if the task asks for those specific records; it does not establish independent discovery or priority.

Unsupported without additional mechanism and evidence: model-weight changes or durable learning; arbitrary information encoding that increases general intelligence; universal recall; proof certification from hashes, compilation, finite fixtures, or a card's status label; arbitrary theorem proving; cheap oracle acquisition; guaranteed access to external repository contents; and scientific novelty/priority. Training would require an actual authorized training path and before/after evaluation. Hosted retrieval would require a tested interface available to the target Astra instance. Neither follows from repository publication.

## Operational bottlenecks and failure modes

- **Reachability:** Public hosting is useful only if the target model can browse/fetch it in its live environment. A URL in instructions is not an enforced tool call. Local `knowledge.py` and SQLite are inaccessible to a remote agent absent an explicit service/tool bridge.
- **Coverage and extraction:** The archive is large, includes non-text objects and runtime material, and some update streams have summaries where linked proof packages were not supplied. Searchable document count and byte integrity are not scientific/source completeness.
- **Recall and ranking:** FTS/BM25 plus curated aliases is a useful baseline, but the design itself warns recall is imperfect. Aliases create maintenance debt and can bias toward already-curated interpretations. A failure to retrieve must not be mistaken for proof of absence.
- **Context and compression:** Cards are authored compressions. Even a complete card can omit a subtle proof condition. Retrieved excerpts are explicitly not proofs. The agent must open decisive lemmas, prerequisites, counterexamples, and cited sources; simply stuffing all cards into context (the full result-card export is ~138k estimated tokens) trades cost for attention and still does not certify comprehension.
- **Proof and priority validation:** Several cards are source-derived/unreviewed or report checks as source-reported. Internal cold reads, compilation, finite tests, checksums, and corpus coverage are scoped evidence. They cannot substitute for an independent proof audit, formalization where appropriate, or priority review.
- **Execution/cost accounting:** Cards frequently state acquisition and computational gates, but the repository does not itself make those services available. Any benchmark that gives the repository condition to one arm but lets it use uncharged browsing, code execution, or extra context will confound the claimed benefit.
- **Freshness and state:** Local index, static mirror, and alternate Sites deployment may be at different snapshots. Mutable `state/` is for current work, while archived source status should remain immutable. A stale site or unmarked task state can silently undo the intended provenance discipline.

## Minimum high-value system changes

Avoid a broad redesign. First make a small target-facing reader interface: one stable entry URL, a version/hash manifest with build time, explicit availability labels per source package, direct exact-card/source reads, and a strict response schema that always returns source IDs plus missing prerequisites and status. Add one query path for “claim + exact proof + counterexample + acquisition/cost gates,” with a clear `NOT FOUND` result. Provide either an explicitly callable local CLI/API for the intended Astra environment or state that the target only has static retrieval; do not imply hosted computation. Keep a short capability contract at the entry point spelling out retrieval, execution, persistence, and training separately.

Second, make only the few selected mathematical checkers runnable through that interface. Pin interpreter/dependencies/input hashes, expose resource caps, retain stdout/errors, and label each output finite/in-scope. Prioritize tasks where the repository already has exact representations and a clear checker, rather than trying to encode every paper into a new general-purpose symbolic language. No value is gained by claiming “executable knowledge” while the external agent cannot execute it.

## Honest capability experiment

Run a preregistered, held-out, paired study with the *same fixed-weight Astra model/version, system prompt, decoding settings, and tool allowance* in every arm. Stratify tasks across the three card domains above and include both answerable tasks and deliberate missing-source/near-transfer controls. Use at least four arms: (A) task only; (B) task plus the same-sized general scientific context; (C) task plus a fixed-size ASTRA entry/core packet; (D) task plus query-selected card and exact cited proof excerpts. If testing executable tools, add a separate arm (E) and charge the same tool setup and calls transparently. Keep per-task context and tool budgets equal where the contrast requires it; record actual fetched bytes, prompt tokens under the best available tokenizer estimate, tool calls, latency, and failures. Randomize task/arm order and conceal gold answers from packet construction.

Score blinded against a fixed rubric: correct theorem/interface and quantifiers; correct supplied/acquired boundary and costs; retrieval of decisive source and counterexample; calibrated abstention when the source is absent; answer correctness on a fresh, independently solved problem; and unsupported-claim rate. A reviewer should verify mathematical answers from source proofs, not card overlap. Report paired effect sizes and uncertainty by domain, plus retrieval recall/precision separately from answer accuracy. An improvement only in cited fact lookup supports “better external memory.” Improvement in novel derivation under the same context/tool budget supports a narrower inference-time reasoning benefit. Neither demonstrates weight training, universal arbitrary encoding, or general intelligence. Release the task set, packet snapshots/hashes, prompts, outputs, scoring rules, exclusions, and negative results so the experiment can be rerun.

The smallest useful pilot is 12–18 tasks (four to six per domain), multiple fresh sessions per arm, and at least one missing-source control per domain. Treat it as feasibility only; it will not give a strong generalization claim. Expand only if the pilot shows a measurable, repeatable gain without increasing hallucination or leaking gold answers into the cards.

## Bottom line for the design decision

Keep the repository-first strategy if the objective is a durable, searchable, provenance-rich research memory that reduces repeated reading and makes prior claims easier to inspect. Treat the likely gain as inference-time retrieval, context organization, and, after a real tool bridge is added, selected deterministic computations. The first decisive experiment is not to encode more knowledge; it is to establish that a fixed Astra instance can reach the right evidence, use it correctly, and outperform an equal-budget baseline on held-out tasks. Until then, “research capability improvement” is a plausible hypothesis, while “breakthrough in Astra intelligence” is unsupported.
