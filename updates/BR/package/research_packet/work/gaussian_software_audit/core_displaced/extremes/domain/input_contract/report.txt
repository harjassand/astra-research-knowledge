2. p checks isinstance(p,int) but does not exclude bool. p=True is accepted as precision 1, whereas p=False is rejected. n explicitly excludes bool. This is a low-severity type-validation inconsistency; it does not demonstrate a mathematically incorrect enclosure.

Float 0.1 is treated as exact 3602879701896397/36028797018963968, whereas string or Decimal 0.1 means exact 1/10. This is correct Fraction semantics but should be stated in an exact-rational input contract; no distribution/enclosure defect follows.
4. NaN coefficients raise ValueError; infinite coefficients raise OverflowError; None raises TypeError. Negative coefficients raise ValueError. These are rejected before n==0 returns, so even a constant coefficient request validates all inputs. Mixed exception types are an API choice, not a soundness issue.
5. force_integral has no Boolean validation. The nonempty string 'False' activates it, and at (n,a,c,p)=(2,1,1,3) raises the branch precondition error. Empty string and None deactivate it; numeric 1 activates it. This can surprise callers passing serialized flags, but is ordinary Python truthiness.
