INDEPENDENT REVIEW OF THE RELEASED DGM LINEAGE RECONSTRUCTION
Reviewer: /root/cycle6_math_capability
Scope: external reference calculation for Astra's meta-research. No Astra owner
programme, API call, new DGM run, or benchmark rerun was performed.

VERDICT

The common-ten-task arithmetic is independently reproduced. The stated narrow
interpretation is defensible: the released main run contains more OBSERVED
verified improving child attempts than the two released ablations. This does not
identify a probability of improvement, a causal effect of improved producer
ability, or recursive scientific intelligence amplification.

The released no_selfimprove implementation and one actual child trace establish
a concrete causal-design limitation: the comparison changes the code tree being
edited as well as the code used by the producer. It is not a controlled swap of
producer capability against an identical evolved target. This qualification does
not establish that the ablation is useless, explain all failures, estimate the
effect of the workspace difference, or invalidate the reported system result.

INDEPENDENT RECONSTRUCTION

I used a separate parser and taskwise reconstruction in check_common10.py. It
does not import analyze_lineages.py. A brace/string lexer splits the concatenated
JSON generation records; json.loads parses the resulting complete documents.
Each task is explicitly recorded as observed success, observed non-success, or
unknown. I checked generation scheduling against the exact child metadata,
matched parent identities, reconstructed archive membership, and confirmed that
every child metadata directory is counted once. The root results were opened
only after this reconstruction, for comparison.

The ten task IDs come from official_repository/swe_bench/subsets/small.json.
All three initial parents have exactly three successes on that fully observed
set. A parent's or child's possible score is the interval

    [observed successes, observed successes + unenumerated outcomes].

A verified gain means child's lower endpoint > parent's upper endpoint; a
verified loss means child's upper endpoint < parent's lower endpoint. This
does not convert missing observations into failures. Both exact score and exact
task identity are used. Empty-patch task IDs count as observed non-successes,
consistent with the official evaluation summaries.

For the main run's first 80 attempts, all listed counts remain unchanged except
attempts (80), and incomplete pairs (35). Its complete pairs are exactly 15
improvements, 16 losses, and 14 ties. All 72 corresponding summary fields in
ROOT_LINEAGE_RESULTS.json match the independent reconstruction.

Important distinction for the fixed-producer run: only seven of its nine
verified gains are complete pairs. Two more are already forced by the observed
intervals despite missing observations:

  child 20250411_191720_971491: parent [3,3], child [4,5];

Its complete pairs instead comprise 7 improvements, 12 losses, and 1 tie.
Two additional losses are forced despite missing observations. Thus the
incomplete-pair column overlaps with certified gain/loss columns. It must not
be described as a disjoint list of wholly unknown comparisons. The root's
"unknown_child_outcome_pairs_10" field is literally the count of incomplete
parent-child pairs; in prose "incomplete pairs" is more precise.

Native archive admission is not proof of improvement. The helper
utils/evo_utils.py:is_compiled_self_improve checks required evaluation keys,
at least one nonempty task patch, and enough submitted issues. It does not
require the child to outperform its parent. "Native archive admission" is an
appropriate label; "verified improvement" is not.

INTERPRETIVE CHALLENGES

1. Verified refers to a released evaluation observation.

The checker verifies bookkeeping from official result lists. It does not rerun
SWE-bench, establish repeated-sampling reliability, or externally verify the
correctness of every accepted software patch. A child can outperform the stored
parent score on these observations without having a larger latent success
probability. Parent scores are reused across multiple comparisons, so one noisy
parent observation induces dependence among descendants.

2. Missingness differs sharply by condition.

The main run has 45 complete comparisons, the fixed-producer run only 20, and
the no-archive run 36. Failure to observe a verified gain is not evidence of a
true non-improving child. Missingness can arise before or during evaluation and
may depend on the producer, target, patch, resource budget, and outcome. The
15/82, 9/80, and 5/80 counts are useful observed productivity records. They do
not estimate comparable Bernoulli probabilities without further assumptions.

Conditioning only on complete pairs does not repair the comparison. It selects
different surviving subsets. Nor can the missingness direction be assumed to
favor or disadvantage one condition. The independent code preserves unknowns
without completing them. Root's separate 60-task censoring analysis should
remain separately scoped; I have not reviewed or recomputed it here.

3. Adaptive selection and shared ancestry prevent iid inference.

The released DGM_outer.py chooses parents using stored performance and child
counts; it chooses task categories using unresolved evaluations. Descendants
share ancestral code and often parents. The ten tasks form a common comparison
set, not a fresh held-out population. A score/depth/chronology association cannot
by itself distinguish improved producer skill, target difficulty, selection,
regression to the mean, adaptation to the task set, or stochastic outcomes.
Higher parent scores also leave less room for net improvement.

4. Equal attempt counts are not equal total resources.

The first-80 comparison removes a two-attempt denominator difference. It does
not equalize generation cost, diagnosis, producer tokens, patching, evaluation
tier, retries, execution failures, or total wall-clock/compute cost. A claim of
more observed useful children per attempted child is narrower than a claim of
more useful research per equal expenditure. No iid errors, significance tests,
causal regressions, or precise global cost-efficiency claims are warranted.

5. Archive improvement and producer improvement are distinct quantities.

A monotonically improving retained best score can arise from fixed-capability
search plus selection. Conversely, most mutations being harmful does not rule
out a valuable search system, and the mean complete-pair decrease does not
invalidate an archive's real best-child improvement. The relevant unobserved
claim is whether newer producers generate more valuable descendants from the
same targets, evidence, evaluation conditions, and total budget. These logs do
not furnish that controlled comparison. They also do not prove its absence.

ACTUAL FIXED-PRODUCER WORKSPACE EVIDENCE

I parsed the original self_evo.md with ast.literal_eval, not just the root's
observed_trace_summary.json. The child is 20250408_005738_095636 in the
swe_dgm_noselfimprove run. Its own metadata names parent
20250407_212519_184190. The released parent model_patch.diff adds an edit_range
command to tools/edit.py, including its schema and implementation.

The child's first actual editor-file read is message index 4. It displays the
original tools/edit.py: only view/create/edit in the command schema and an
explicit absence of partial or line-range editing. The text contains no
edit_range. This is a concrete observed target lacking an inherited parent
feature, not merely an inference from a conditional statement in source.

The official self_improve_step.py explains the mechanism. Parent patches are
applied before producer execution only when run_baseline is not
'no_selfimprove'. The invoked producer is /dgm/coding_agent.py and its target
git directory is /dgm/. Thus skipping patches leaves both the executing agent
and its editable target in the base tree. Diagnosis still refers to the selected
parent. Downstream evaluation applies patch chains separately; this does not
make the editable target identical during production.

This supports the following limited statement:

  The released fixed-producer ablation is not a clean isolation of producer
  capability while holding the edited parent target constant. A difference
  between its outcome and the main run can include target-workspace alignment
  and integration effects.

Do not strengthen it to any of the following:

  * all fixed-producer attempts edited incompatible code;
  * the absent feature caused this child's score or all baseline failures;
  * a clean fixed-producer baseline would match or beat the main system;
  * this implementation makes the paper's broad system findings false;
  * all reported performance improvements are artifacts.

An actual causal producer comparison would hold a selected evolved target
snapshot and diagnostic information constant, then provide two separately
executed producer versions equivalent access to it. A broader system comparison
can intentionally vary the entire loop, but should be described as such. No
such additional experiment was run by this reviewer.

RECOMMENDATION TO ROOT

Retain this analysis as a substantive empirical warning against identifying
downstream gains with recursive improvement of the ability to invent. Present
the positive observation too: the main run did create 15 recorded children
with common-task gains and the released archive can preserve advances despite
many losing mutations. The evidence supports distinguishing these capabilities;
it does not support declaring that self-improvement is impossible or that Astra
should abandon independent scientific programmes.

The strongest transferable inference is experimental: a future second-generation
amplification claim must compare production of further valuable improvements
while holding target, evidence, verification, and expenditure appropriately
fixed. The present analysis identifies why this is a missing empirical quantity,
not a demonstrated improvement to Astra's own discovery process.
