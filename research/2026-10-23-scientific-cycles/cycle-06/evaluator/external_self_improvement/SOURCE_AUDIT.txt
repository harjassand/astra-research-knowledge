DARWIN GÖDEL MACHINE — PRIMARY SOURCE AND RELEASED-DATA AUDIT
Prepared for Astra Cycle6 meta-research, 2026-10-22-labelled review
Status: independent source/record analysis; no DGM execution or paid resources.

CENTRAL FINDING

The released data permit an actual analysis of parent/child coding outcomes,
including newly observed solved task IDs. They do not directly measure a clean,
matched improvement in the ability to produce improvements. This is not just a
generic correlation warning: the released baseline implementation changes both
the producer and the code workspace it edits. One actual baseline trace confirms
that its workspace lacks a previously accumulated parent improvement.

The finding narrows what the DGM evidence can establish. It neither disproves
self-improvement nor explains the full outcome difference between the methods.

2. SOURCE-VERSION BOUNDARY

The pinned source commit postdates the March/April run IDs in the SWE release.
The per-agent metadata do not bind runs to a repository commit, Docker image
digest, full package lock or exact evaluator source version. No exact
source-to-historical-run equivalence is established. Source code below describes
the released implementation; source/record agreement is checked where possible.

A relevant corroboration is available: an actual recorded baseline workspace
has exactly the absence of parent changes predicted by the current source.
This is stronger than identifying an unexecuted code-path discrepancy, but
we inspected one such trace and do not assert universal run behavior.

3. EXACT FIXED-PRODUCER BASELINE SEMANTICS

The paper's Appendix C.4 describes the intended baseline abstractly as the
initial agent modifying a selected evolving parent, g0.modify(p). That would
be a useful conceptual control if the edited target and proposal were held
fixed while only the producer changed.

In the released self_improve_step.py:
  - get_model_patch_paths collects the selected parent's ancestry patches.
  - Lines 294-299 apply those patches inside the improvement container only
    when run_baseline is not no_selfimprove.
  - diagnose_problem receives the selected parent and its patch_files in
    both conditions. The separate diagnostic model is o1-2024-12-17.
  - get_diagnose_prompt_swe supplies the diagnostician base source plus the
    patch texts and parent evaluation records.
  - get_problem_description_prompt passes the diagnostic recommendation and
    problem description to the implementing coding agent, not a separate
    parent workspace. coding_agent.py reads and edits its supplied /dgm/ tree.
  - The patch produced by that implementation is appended to the selected
    parent's patch list for evaluation (self_improve_step.py, line381).

Consequently the source's fixed-producer branch is not simply a frozen agent
editing the identical evolving target workspace used by the main method.
The producer, visible edited tree, and subsequent patch-composition context
are intertwined. Patches created against one base can behave differently when
applied over another. This is a concrete possible confound, not an assertion
that it explains the observed performance gap.

4. EVALUATOR AND SELECTION SEMANTICS

The released SWE task lists contain 10 initial, 50 additional and 140 further
tasks. The source first evaluates the small set, then conditionally evaluates
the next set if enough small-set tasks pass. Per-agent metadata in this release
show counts near 10, 60, 200, plus incomplete counts. The fixed-producer and
no-open-ended released runs have no 200-task metadata, whereas the main run
does. Raw overall accuracy scores therefore are not automatically matched
measurements of the same task distribution.

get_all_performance sums reported resolved/submitted counts across matching
result JSON files and concatenates reported outcome IDs. It does not correct
for missing enumerated IDs or tier selection. In the downloaded records, some
declared submitted totals exceed the total enumerated resolved/unresolved/
empty-patch IDs. The initial record declares 60 but lists 58 unique IDs; the
two absent IDs are sphinx-doc__sphinx-7985 and sphinx-doc__sphinx-8475. Treat
missing outcomes explicitly; do not silently assign them a verified result.

The archive's compiled/eligible designation is an operational filter. The
released is_compiled_self_improve requires the score/outcome keys, at least
one nonempty task patch, and a minimum evaluated count. It is not a full proof
that the agent can improve itself. A score or compiled flag is not independent
validation of that higher-order capability.

Parent selection favors performance through a sigmoid and discounts parents
with more functioning children. A diagnostician then chooses features from
parent errors and fixed generic categories. Parent score, target difficulty,
available headroom, accumulated design, ancestry, selection opportunities and
proposal choice consequently covary. Children in a generation are concurrent;
within-generation order must not be treated as a genuine sequential knowledge
history. The saved parent score can also reflect later expanded evaluation,
so a retrospective metadata value may differ from the score used at selection.

6. COST IDENTIFIABILITY

The paper gives approximate whole-run SWE API expenditure of $22,000 for main
and $10,000 for each of its two original ablations. It explicitly acknowledges
the cost difference. The recovered per-agent summaries have no token counts,
billable usage, per-attempt monetary cost or reliable elapsed-time fields.
The ZIP index has no top-level cost ledger. Source timeout limits are limits,
not measured resource consumption; serialized transcript lengths are not
billable-token receipts. Actual model calls can differ after code evolution.

We therefore cannot calculate a defensible matched-dollar improvement rate or
claim equal resources merely because attempt counts are close. Nor can the
entire cost difference be declared the cause of the outcome difference. Some
extra evaluation cost may be downstream of reaching stronger candidates.

7. WHAT A LINEAGE REANALYSIS CAN AND CANNOT TEST

Useful descriptive questions with these records:
  - On the same observed tasks, do higher-scoring parents produce more usable
    successors, more observed new passes, or more net gains per attempt?
  - How often is child-score improvement just persistence of parent successes,
    task-tier composition, recovery from missing outputs, or stochastic churn?
  - Does a trend survive restricting to common tasks and the same number of
    attempts, and reporting incomplete outcomes separately?

Unsupported causal conclusions:
  - A parent-score/child-score correlation proves improved invention ability.
  - The winning lineage or rising cumulative best demonstrates acceleration.
  - A fixed-producer aggregate gap isolates producer skill independently of
    workspace/patch semantics, target path, proposal path or total resources.
  - Either a positive or negative correlation rules on Astra's much broader
    scientific-intelligence ambition.

The underlying identification issue is elementary but consequential. Let
U(a,p,q,b) denote the outcome of producer a modifying target p with proposal q
under budget b. A self-modifying lineage mostly observes moving diagonal
entries U(a,a,q_a,b_a). It does not identify the effect of changing a while
holding p,q,b fixed. Even a clean g0 baseline on a separately evolving target
trajectory generally does not supply those missing matched entries.

A discriminating future test would cross at least two producer versions on
the same held-out target snapshots and the same independently generated
proposals, with equivalent resource caps and an evaluator unaffected by the
producer. It would measure genuinely new validated capabilities, regressions,
and total cost. A next generation would then need to improve the production
of a further gain, rather than merely inherit the first gain. This is a test
design consequence, not an experiment executed in this audit.

8. CONSEQUENCE FOR ASTRA

External self-modifying-agent results justify taking executable improvements
seriously; they do not license assuming that a larger stock of solved problems
has already increased the rate or depth of new discovery. Astra should retain
its demonstrated mathematical reuse and accumulated capability while keeping
the stronger recursive-amplification claim unestablished. Its evidence must
connect acquired capital to a distinct receiving investigation's new inference
or construction, then to a subsequent improvement-generation step.

The current audit's original contribution is bounded: recovery and analysis
of released evidence previously hidden inside a large archive, and a concrete
source-and-trace control discrepancy that matters to causal interpretation.
It is not a new scientific-intelligence architecture, a DGM replication, or a
demonstration that a proposed Astra research method works.
