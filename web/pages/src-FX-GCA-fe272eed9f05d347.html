# Exact JSON input correction, version 2

The independent compiler review found a real input-boundary defect in
version 1: ordinary `json.loads` converted decimal JSON numbers to binary
floats before `Rational(str(x))` ran. The literal
`1.00000000000000000001` could therefore become the rational number 1.
This affected the exact-input contract; it did not change the mathematical
theorem or the supplied rational-string fixtures.

Before correction, the compiler, its general receipt, and the original
manifest were preserved byte-for-byte as
`flat_completion_compiler.v0001.py`,
`GENERAL_COMPILER_RECEIPT.v0001.json`, and `FILE_MANIFEST.v0001.json`.
`PARSER_CORRECTION_BASELINE.v0001.json` records those hashes and the
protected proof hashes. The original `FILE_MANIFEST.json` remains the
historical version-1 manifest; use `FILE_MANIFEST.v0002.json` for the
corrected packet.

The corrected JSON loader passes each decimal/scientific token directly to
SymPy Rational. It rejects nonfinite constants. The scalar API also rejects
pre-parsed Python/SymPy floats, since their original decimal precision may
already be lost. Exact integers, SymPy rationals, and finite rational
strings remain accepted. Invalid schema, booleans, non-rational strings,
zero denominators, and negative H reserves raise an input error. The CLI
returns exit code 2 on invalid input and does not create a result file.
Negative coefficients remain valid inputs.

The compiler self-check passes 14 groups, retaining its original 11
mathematical checks and adding exact decimal, exact scientific-notation,
and 12-invalid-fixture groups. `PARSER_CLI_REPLAY.v0002.py` passes six
end-to-end groups: decimal and scientific inputs give complete output
certificates identical to exact rational-string counterparts, the original
rational example remains unchanged, and negative reserve, NaN and boolean
inputs fail with exit code 2 and no output. The exact scientific reserve is
1234567890123456789 / 10^41.
