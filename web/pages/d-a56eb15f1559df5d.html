## A general direct-EF naming obstruction

Keeping plus(p)=p while naively using minus(p)=the string `p-` is not
freshness preserving. Let an earlier source row be A5 at ~p, containing
only original atom p. A subsequently defined alias e=`p-` with body p is
actually fresh in the source. But the prior positive target row already
contains `p-` as minus(p). A target extension e+ := p therefore violates
standard EF freshness. This is an actual source-admission versus target
freshness mismatch, not a semantic refutation of the closed-Frege map:
closed theorem proofs tolerate atom identification.

The repair preserves all positive names and allocates each negative name
outside the entire original atom set, including future extension names,
and outside all previously allocated negatives. The own executable
allocator also tests a deliberately reserved generated-name candidate.
Its 2V signed atom identifiers are injective. A fresh source e then has
both coordinates absent from prior translated rows and body. Generated
name bytes require an explicit naming budget; node-linear translation
does not imply constant-cost identifiers. No direct arbitrary-name EF
installer is claimed by this bounded replay.
